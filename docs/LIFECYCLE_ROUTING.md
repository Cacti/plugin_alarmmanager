# Lifecycle and routing

Stream identity is source + source_instance + alarm_key + mode. Sequence must increase across episodes. Equal/stale events do not alter current state. A new raised episode supersedes an active predecessor and resets acknowledgment. Updates, reminders and recovery require the current active episode; recovery for an old episode cannot advance the current stream sequence. Closed episodes cannot reopen. Occurrence events advance ordering without activating or replacing a condition. Acknowledgment is separate internal state; administration UI comes later.

Processing atomically commits state, episode history, decisions, destination jobs and completion under a valid fenced lease. Observe mode has separate shadow state and records would-route decisions without deliveries; it consults live acknowledgment policy. It cannot consume centralized event identity or notification ownership.

Apply a complete bounded version-1 JSON configuration with cli/configure.php. See examples/routing.json for REST API + webhook fan-out. Rules run by ascending priority then ID; selectors combine source, severity, transition, device, collector and tags. All selected tags must match. Explicit stop ends rule evaluation. Profiles select endpoint IDs; optional event context.routing_profile_id selects a profile. Duplicate endpoint selection is recorded and the first selected policy wins. Decisions pin the immutable configuration revision used for processing.

Suppression considers disabled destinations, source suppression, maintenance, acknowledgment, cooldown and duplicate fingerprint. Recovery bypasses acknowledgment/cooldown/duplicate suppression. Cooldown is episode-local. Schedules use event occurrence time, named IANA timezone, weekday and half-open HH:mm windows; overnight windows include the previous day's start. Equal start/end represents a full day. Configuration validation bounds selectors, rules, endpoints, JSON and policies; credentials are not part of this configuration yet.

Each centralized event/endpoint receives a stable idempotency key and at most one delivery job. Destination retries are independent: a successful webhook is not resent because its REST API sibling failed. External effect deduplication still requires receiver support, especially after a send succeeds but completion acknowledgment is lost. Phase 5 adds REST API/webhook/email/script handlers; WebSocket remains phase 9. Current transport definitions/credentials are resolved at attempt time as documented in DELIVERY.md.
