# Credential lifecycle and poller provisioning

Servcheck's inspected pattern stores JSON credential records encrypted with a per-installation key from Cacti settings_user. Alarm Manager uses its own setup-generated 32-byte CSPRNG key at owner 1/name alarmmanager_key and never borrows servcheck's key or generates one during saves. Missing/malformed keys fail closed; existing keys survive install/upgrade. Missing keys over encrypted records cannot be regenerated by setup.

Schema v3 stores one endpoint-bound authenticated record in plugin_alarmmanager_credentials. Format am1: plus canonical base64 of 12-byte random nonce, 16-byte GCM tag and ciphertext; AES-256-GCM additional authenticated data binds format version and endpoint ID. Wrong keys, truncated tags, modified nonce/body/tag, unknown format and copied ciphertext under another endpoint ID fail. This requires OpenSSL; no crypto library is fetched. Sensitive function arguments are hidden from PHP exception traces. SQL helper logging is disabled and DEBUG_SQL_FLOW blocks all secret operations. Protect DB backups: settings_user contains the decryption key, so a full DB copy is secret material.

HTTP credential JSON accepts headers and optional basic.username/password. Header names are unique ignoring case; CR/LF/control bytes and transport-owned headers are refused. Authorization: Bearer ... and API-specific authentication headers are stored here. Basic auth cannot overlap Authorization. Credentials are HTTP-only; Cacti's SMTP credentials remain in its own mail settings. Script credentials are not injected.

Save credentials using an owner-only file (0600, owned by the executing account, no symlink), or stdin to avoid a plaintext file. Do not use tokens/passwords on the command line:

```sh
php cli/credentials.php --save=1 --file=/secure/endpoint1.json
php cli/credentials.php --save=2 --file=php://stdin
```

An input shape is {"headers":{"Authorization":"Bearer REPLACE_WITH_REAL_TOKEN"}}. The placeholder is not a usable credential. Set transport.credential=true only after provisioning. Neither action prints secrets. Phase 6 provides an administrator-only POST/CSRF credential editor showing configuration status and blank replacement inputs. It never returns saved secrets or keys; backup/restore/provisioning remains CLI-only.

## Backup, restore and rotation

```sh
php cli/credentials.php --backup-dir=/secure/new-backup
php cli/credentials.php --rotate
php cli/credentials.php --restore=/secure/backup/credentials.json --key-file=/secure/backup/key.txt --replace-local-credentials
```

Backup requires a new absolute directory, creates it 0700 and writes new 0600 credentials.json and key.txt files without overwrite. The exported key and ciphertext snapshot match even during rotation. Verify both files exist after success; a filesystem failure can leave an incomplete directory, which must not be used as a backup. Keep the key separately in protected offline storage and transfer neither file through source control, chat, previews or ordinary logs. Use encrypted storage/transfer for both and protect the source settings_user record. Backup routing configuration separately; it contains no credential values.

Restore is an explicit replacement of the entire local credential set and canonical key. It validates every record before writing and requires corresponding HTTP endpoint IDs already configured locally. It can recover a missing/malformed key only when the supplied original key authenticates the supplied records. Failed validation/storage rolls back without partial replacements. Never restore ciphertext alone and generate a new key. Empty bundles explicitly replace the credential set with no records; use the replacement flag carefully.

Rotation takes a transaction lock on the canonical key, authenticates and re-encrypts all records with a new random key, then updates settings_user in the same commit. Saves/backup/restore serialize on that lock. Loads use one transaction snapshot for key and ciphertext. Failure leaves the old key/records intact. Capture a new protected backup after rotation; retain old matching backups for historical DB restores. Rotation is local, not an automatic fleet operation. Existing requests may finish using already-loaded plaintext.

## Authorized remote pollers

For each poller, install the plugin locally (normal Cacti plugin install/upgrade provisions the schema and setup key — there is no separate local-setup command), apply its complete routing/transport configuration (`php cli/remote.php --configure=/secure/routing.json` or the export flow below) and provision its certificate/attachment files. Then either save each credential locally (independent setup key, preferred for scoped destinations), or securely transfer a reviewed credential bundle and matching key and run the explicit restore command locally. Restore replaces that poller's entire local key/set; filter/re-encrypt a scoped bundle if it should not receive all credentials. Possession of ciphertext does not authorize a poller and does not make it usable without the matching key. Use least-privilege destination credentials and preserve endpoint ID binding.

All commands use Cacti's offline/local bootstrap. Operational credential tables and the setup key must be excluded from destructive/automatic main-to-remote overwrites. No automatic replication or secret transfer is added. Tests prove ciphertext-only failure and successful provisioned HTTPS from a separate poller-local database. Full Cacti remote deployment, disconnect/reconnect and history reconciliation are phase-8 qualification; they are not claimed by this database-adapter fixture.
